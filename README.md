# Cozy Tiny Space — Renter-Friendly Small Space Organization

A Google SEO-first, Pinterest-supported micro-niche blog: practical storage and
organization for renters in small apartments. No drilling, no permanent changes,
no lost deposit.

**Status:** v1 complete — 30 articles, 5 categories, all pages, verified build.
**Stack:** Astro 5 + TypeScript + Tailwind CSS v4, Content Collections + MDX,
Cloudflare Pages (static, no adapter). **Site URL (placeholder, NOT purchased):**
`https://cozytinyspace.com`

## Quick start

```bash
npm install
npm run dev      # local dev server
npm run build    # astro build + search index + Pagefind
npm run preview  # preview the production build
```

Node 20+ and npm 10 required (developed on Node v24 / npm 10).

## Change the domain — one place

The domain lives in **two files** that must stay in sync:

1. `astro.config.mjs` — `site: 'https://cozytinyspace.com'`
2. `src/utils/site.ts` — `SITE.url`

Change both to the purchased domain before launch. The domain
`cozytinyspace.com` was checked available on 18 Nov 2026 but is **not
confirmed and not purchased** — verify availability again before buying.

## Deploy (Cloudflare Pages)

1. Push the repo to GitHub (or GitLab).
2. Cloudflare Dashboard → Workers & Pages → Create → Pages → connect the repo.
3. Build command: `npm run build` · Output directory: `dist`
4. Framework preset: **Astro** (or "None" with the same build command).
5. Set the custom domain once purchased. The `public/_redirects` file is not
   used; the `robots.txt` and sitemap are generated by the build.

## Content workflow

- Articles live in `src/content/articles/*.mdx` (Content Collections).
- Categories in `src/content/categories/*.md`, author in
  `src/content/authors/hamza-hameed.md`.
- Every article's frontmatter is validated by the Zod schema in
  `src/content.config.ts` (description 145–165 chars, FAQ 4–6, tags ≤ 4,
  `draft` default `false`, `pillar` only on the 5 cluster pillars).
- Run the quality gate before every build: `node scripts/validate-content.mjs`
  (see "Quality gates" below).
- Add a new article: copy an existing MDX, fill the frontmatter, write the
  body (see the article template in the structure doc), add a 900×1200 SVG
  in `public/images/<category>/` (or a real photo — see "Image policy"),
  run the validator, then build.

## Publishing schedule (gradual rollout — do NOT dump all 30 at once)

The 30 articles ship with `draft: false` so the site is complete, fully
interlinked and verifiable in v1. **Do not publish all 30 on day one.** The
planned pace (from the structure doc):

| Phase | Articles | Dates |
|---|---|---|
| Week 1–2 | 4 (kitchen pillar + no-drill kitchen, bedroom pillar + under-bed) | 24–27 Nov 2026 |
| Week 3–4 | 4 | 1–4 Dec 2026 |
| Month 2 | 8 | Dec 2026 – Jan 2027 |
| Month 3 | 8 | Jan 2027 |
| Month 4 | 6 | Jan – Feb 2027 |

**How to hold an article back:** set `draft: true` in its frontmatter. Drafts
are excluded from pages, listings, the sitemap, RSS and search. This is the
rollout mechanism — **not** date-gating.

**Why not date-gating?** Every pillar article links to all 5 of its supporting
articles, and every supporting article links back to its pillar. If a pillar
went live while a supporting article was date-gated (404), the pillar would
contain dead links. The `draft` flag keeps the link graph intact: only flip
an article live when everything it links to is also live. **Rule: a pillar's
links must only point at live articles.**

## Indexing — what the build does, and what it cannot do

The build maximises the odds of fast indexing (the lesson from the owner's
first site, Outfit Edits, where 28 articles ended up crawled-not-indexed from
thin/duplicate volume publishing):

- Every article passes three gates before it counts as done — **DEPTH**
  (substantive, specific advice, no filler), **Google SEO** (unique meta
  description 150–160 chars, distinct target query per article, proper
  H1/H2s, 1–2 outbound links to authoritative sources, FAQ) and
  **Pinterest SEO** (keyword-first title and description, 3:4 portrait image).
- Zero orphan articles: every article is linked from its category page, from
  its pillar or a sibling, and from the homepage or a pillar (verified by
  `scripts/validate-content.mjs`).
- Complete sitemap (auto-generated), `robots.txt` (allows `/`, disallows
  `/search/`), canonicals on every page, JSON-LD (BlogPosting, WebSite,
  BreadcrumbList, FAQPage).

**But the build cannot guarantee fast indexing.** After deploy you must:

1. Submit the site and sitemap in Google Search Console.
2. Request indexing for the first articles (a few per day, not all at once).
3. Wait. A brand-new domain still takes weeks to earn consistent crawling,
   no matter how clean the build is.

## Image policy (owner-confirmed — read before touching any image)

**1. BEST — original photos taken by the owner with a phone.**
This is the long-term image strategy. The SVG illustrations in this repo are
**placeholders only and MUST be replaced with original photos before
launch** — they are still what the homepage, category pages, article cards,
og:image and the Pin-it button use. Real photos are what Google, AdSense and
Pinterest reward; an illustration placeholder is not a substitute for a real
photo of a real shelf in a real apartment. Replacing the SVGs with real
photos is still required before launch, even though article feature visuals
are now Instagram embeds (see point 3).

**2. Acceptable supplement — free-licensed stock.**
Unsplash or Pexels (free license, no attribution required) may supplement
original photos where the owner cannot shoot a shot — for example a wide
room view. Prefer original photos wherever a specific product or method is
shown. Free stock is also the correct source for **Pinterest pins** (see
point 3) until original photos exist.

**3. Instagram — official embeds ONLY. NEVER download and re-upload anyone's
Instagram photos.** Not even with credit. **Credit is not permission.**
Downloading a photo from Instagram (or any social site) and uploading it
here is copyright infringement. **No Instagram image file was downloaded
for this site, ever.**

Instead, every article's feature visual is an **official Instagram embed**:
the standard `instagram-media` blockquote (`data-instgrm-permalink` = the
public post URL) plus Instagram's own `embed.js`, loaded once per article
page. The photo is served by Instagram itself, the post stays the creator's,
and **no permission is needed** for an official embed. Every article shows a
visible credit line under the embed: "Photo: @username on Instagram",
linked to the original post. The full list of the 30 embedded posts (one per
article) is in `instagram-embeds.md` next to this project.

Trade-offs to know:
- Embeds are slower than a local image and add a third-party script, so
  they cost a little speed and SEO weight on article pages. That is the
  price of a real photo without taking anyone's file.
- **Embeds cannot be pinned.** Pinterest needs an image file, and an embed
  has none. The Pin-it button therefore still points at the article's SVG
  illustration, and **Pinterest pins still need real image files** — the
  owner's own photos or free stock — before pins are worth making. Do not
  pin the SVG placeholders.

**4. Amazon / retailer product images — only after an Associates account is
approved.** Do not use Amazon or retailer product images until the site has an
approved Amazon Associates account. Until then, use original photos or
free-licensed stock.

**Practical rules:**
- Feature images must be **3:4 or 2:3 portrait** (900×1200 or 800×1200).
- Never hotlink an external image — every image *file* on the site lives in
  `public/images/`. The one exception is the Instagram embed: it is not a
  hotlinked image, it is Instagram's official embed, and the photo is served
  by Instagram itself.
- To replace a placeholder: put the new file at the same path the article's
  frontmatter `image` field points to (e.g.
  `public/images/kitchen-storage/<slug>.jpg`), update `imageAlt`, and rebuild.
  This swaps the card, og:image and Pin-it image; the Instagram embed on the
  article page itself is unchanged (to change the embedded post, edit the
  article's `instagramUrl` / `instagramCredit` frontmatter instead).
- Regenerate images any time with `npm run images` (re-creates the SVG
  placeholders — it will overwrite manual SVG edits, not photos).

## Quality gates

`node scripts/validate-content.mjs` — fails the build if any of these break:

- All 30 expected slugs exist; exactly 1 pillar per cluster.
- Meta description 145–165 chars (target 150–160), unique keyword per article.
- FAQ 4–6 items, tags ≤ 4, feature image exists on disk, category valid.
- Body: `## Common Mistakes` and `## Conclusion` present; no H1 in body;
  each of the 6 solution labels (`Required space:`, `Installation:`,
  `Approximate dimensions:`, `Rental-friendly limits:`, `Pros:`, `Cons:`,
  `Suitable products:`) appears ≥ 4 times (except the move-out checklist,
  which is room-by-room by design).
- ≥ 3 internal links per article, every internal target exists, no orphan
  article (each linked from ≥ 1 other article).
- ≥ 1 outbound link per article; **FAIL** on any `tag=` / `amzn.to` /
  `amazon.` affiliate-style link.
- Word-count floors: pillar ≥ 1,800 words, supporting ≥ 1,200 words.

## Search

`npm run build` runs `astro build`, then `scripts/build-search-index.mjs`
(generates `public/search-index.json` from the MDX files), then Pagefind
(`pagefind --site dist`). The search page (`/search/`) tries Pagefind first
and falls back to the JSON index. If Pagefind is unavailable in the build
environment, the build still succeeds and the JSON fallback serves search
(the build script prints a note in that case).

## Newsletter

The newsletter form (`src/components/NewsletterForm.astro`) is a placeholder:
set `ESP_ACTION` to the form endpoint of the chosen provider (Buttondown or
Kit) and `ESP_FIELD_NAME` to its email field name. With `ESP_ACTION` empty,
the form does **not** POST anywhere — it intercepts the submit and shows an
honest "launching soon" message with the author's email instead.

## Ads

Reserved-height, labelled ad slots only (`src/components/AdSlot.astro`) — no
real ad code. AdSense comes later; auto-ads stay off. The slots keep layout
shift at zero when ads are added.

## Keystatic admin (`/keystatic`)

Keystatic **is included in v1 and the build passes with it**. The site is
`output: 'static'` with the Cloudflare adapter, so all content pages are
prerendered and only the `/keystatic` admin route (plus `/api/keystatic`) is
served on demand — the same pattern as Outfit Edits. The admin is configured
in `keystatic.config.ts` with collections for `articles` (5 categories),
`authors` and `categories`.

**Before the admin can be used**, the owner must create the Keystatic Cloud
project — the config currently points at a placeholder:

1. Create a project at https://keystatic.cloud and connect it to this site's
   repo.
2. In `keystatic.config.ts`, replace the placeholder project slug
   `cozy-tiny-space/cozy-tiny-space` with the real `<org>/<project>` slug.
   Do NOT reuse the Outfit Edits project (`fashionblog/fashion-blog`).
3. Deploy to Cloudflare Pages — the admin is served from the deployment
   (`/keystatic/`), and `robots.txt` already disallows it from search engines.

Until steps 1–2 are done, the site builds and deploys fine; the admin simply
cannot sign in. Content can still be edited as MDX files in Git in the
meantime (see "Content workflow").

## Design system

Warm neutrals + one terracotta accent. Tokens in `src/styles/global.css`:
paper `#FAF7F1`, ink `#1C1917`, accent `#B4532A`. Fonts: Fraunces (display
serif) + Public Sans via Google Fonts, system fallbacks. Animations are
CSS-only: scroll-reveal (`animation-timeline: view()` with a visible-by-default
fallback), native View Transitions, image hover zoom (transform only), and the
before/after slider (native `<input type="range">` + `clip-path`). All motion
is gated by `prefers-reduced-motion`. Performance budgets: LCP ≤ 2.5s,
CLS ≤ 0.1, INP ≤ 200ms.
